# 🍩 FSD Architecture

## Purpose

This document describes the architectural direction of FSD.

FSD evolves from the AI coding assistant concept.

The architecture described here represents the target organization of FSD concepts.

For the evolution strategy, see:

`FSD-IMPLEMENTATION-STRATEGY.md`

---

# Architecture Principles

FSD architecture should:

- preserve compatibility;
- minimize unnecessary complexity;
- allow gradual evolution;
- separate responsibilities.

---

# Conceptual Model

The target FSD model is:

User  
↓  
CLI  
↓  
Kitchen  
↓  
Bench  
↓  
Oven  
↓  
Recipe  
↓  
Baker  
↓  
Skill  
↓  
Donuts (Artifacts)  
↓  
Display  
↓  
Fridge (Archive)

This represents the intended organization of responsibilities.

The current implementation may differ during migration.

---

# CLI

The CLI is responsible for user interaction.

Responsibilities:

- receive commands;
- validate input;
- start workflows;
- present results.

---

# Kitchen

Kitchen is the conceptual project preparation layer.

Responsibilities:

- provide configuration;
- provide preferences;
- provide project context.

Kitchen represents the environment required before execution.

---

# Bench

The Bench is the workspace directory where task definitions, inputs, and work items are placed before execution.

Responsibilities:

- host active task files and input specifications;
- store workspace state and temporary execution artifacts;
- provide the directory structure for files processed by the Oven.

---

# Oven

The Oven is the execution coordination layer.

Responsibilities:

- manage execution lifecycle;
- coordinate components;
- invoke workflows.

The Oven should remain independent from specific development domains.

---

# Recipes

Recipes represent workflows.

A Recipe defines:

- execution steps;
- required Bakers;
- required Skills.

Recipes describe how work should be performed.

---

# Bakers

Bakers are the FSD terminology for AI Agents.

A Baker represents a specialized AI worker.

A Baker contains:

- responsibilities;
- craft description;
- available skills.

The Baker concept does not necessarily replace the technical Agent implementation.

---

# Craft

Craft describes the specialization of a Baker.

Craft is descriptive metadata.

Craft does not execute behavior.

Execution capabilities are provided by Skills.

Examples:

- Backend Engineering;
- Frontend Development;
- Software Quality;
- Architecture.

---

# Skills

Skills are executable capabilities.

A Skill should be:

- focused;
- reusable;
- predictable.

Skills remain compatible with the broader AI agent ecosystem.

---

# Context

Context represents information provided during execution.

Examples:

- project knowledge;
- rules;
- documentation;
- configuration.

Context should be loaded intentionally and efficiently.

---

# Donuts

Donuts are outputs generated by FSD.

Examples:

- source code;
- documentation;
- plans;
- reports;
- generated files.

---

# Display

The Display is the showcase layer where completed tasks (`status: done`) and delivered Donuts are placed for user review and inspection.

Responsibilities:

- expose completed task artifacts and deliverables to the user;
- host active completed items before long-term archiving;
- serve as the presentation stage for finished work.

---

# Fridge

The Fridge is the archiving and long-term storage layer for completed tasks, past contexts, and historical execution artifacts requested by the user.

Responsibilities:

- store archived task definitions and past work items on user request;
- preserve execution logs, historical metadata, and old execution states;
- serve as cold storage to keep the active Bench clean and focused.

---

# Directory Structure

The conceptual model separates user-facing project workspaces from internal CLI state.

### 1. User-Facing Workspace (`nook/`)

The `nook/` directory serves as the user-friendly interface store where developers manage tasks, contexts, and deliverables:

- **`nook/kitchen/`**: Project rules, global settings, and user-provided context.
- **`nook/bench/`**: Active workspace hosting input task files (`status: in_progress`).
- **`nook/recipes/`**: Declarative workflow definitions.
- **`nook/bakers/`**: Specialized AI worker definitions and craft metadata.
- **`nook/display/`**: Showcase area hosting finished deliverables (`status: done` Donuts).
- **`nook/fridge/`**: Archive holding past completed work items and historical tasks.

### 2. System Directory (`.fsd/`)

The `.fsd/` directory contains internal, "under the hood" execution mechanisms managed automatically by the CLI:

- **`.fsd/oven/`**: Execution engine orchestration state and runtime metadata.
- **`.fsd/cache/`**: Internal resolution caches and temporary process data.
- **`.fsd/logs/`**: Execution logs and diagnostic metadata.

```text
my-project/
├── nook/                  # User-friendly workspace directory
│   ├── kitchen/           # Configuration, rules, and project context
│   ├── bench/             # Active tasks in progress
│   ├── recipes/           # Declarative workflows
│   ├── bakers/            # Specialized AI workers
│   ├── display/           # Finished Donuts (status: done)
│   └── fridge/            # Cold storage archive
│
└── .fsd/                  # Internal system & execution state
    ├── oven/              # Runtime coordination engine
    ├── cache/             # System caches
    └── logs/              # Execution logs
```
